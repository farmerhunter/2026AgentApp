# 学途智伴 · 对话示例文档


## 从学习记录，到复习方向

设计灵感与用户痛点

学途智伴的设计灵感来自日常学习生活。使用错题本整理试卷和作业时，我发现三个问题：

### 01｜整理耗时

抄题、拍照和分类占用大量时间，真正用于理解错误和订正的时间被挤压。

### 02｜问题分散

错题按页保存，难以联系教材知识，也不容易发现不同题目背后的共同问题。

### 03｜复习缺少重点

记录越来越多，却难判断哪些问题应优先处理、哪些步骤已有变化，以及下一步怎样练习。

因此，我设计了学途智伴：以教材建立知识参照，把练习中的原始作答转化为有依据的学习发现，经用户确认保留学习记忆，再通过周报形成复习重点与行动建议。

教材参照 → 练习证据 → 学习发现 → 学习记忆 → 周报行动

## 教材上传与知识整理

把教材组织成后续分析可以引用的知识参照。

### 1.1 操作入口与材料信息

在 Demo 的“学习内容理解”中，用户填写学科、年级、资料标题及页码范围，点击“选择 PDF 文件”进入示例教材状态，再点击“分析教材”，查看章节、学习单元和知识点的组织方式。该页面用预置材料呈现教材上传与摘要流程；App 使用已完成离线整理并发布的知识地图。

### 1.2 教材摘要 Skill 如何组织内容

教材摘要 Skill（textbook_summary）规定整理方法和输出结构。离线整理时，将教材信息与提取后的文字交给 Hermes，按照章节划分学习单元，再提炼知识点名称、内容概括及其所属位置。对于材料中无法确定的内容，保留核对标记，由人工对照教材确认。

整理结果保留教材身份、章节层级和知识点之间的关系。这样，后续分析既能找到某个知识点，也能知道它处于什么学习单元，而不必每次将整份教材重新放入任务。

教材文字与信息 → Skill 辅助整理 → 人工核对 → 发布知识地图

### 1.3 从摘要到可追溯的知识地图

教材摘要采用 textbook_content_summary 结构；当前知识地图采用 textbook_knowledge_map 结构。整理结果按地图规范转换并校验后发布。地图身份、版本和知识点编号共同确定引用位置，使题目记录与分析结果使用一致的知识参照。

应用读取地图时核对文件摘要值与版本登记，保证使用的文件与登记版本一致。分析任务再提取相关节点，作为解释概念、关联题目和组织复习建议的上下文；对学习问题的判断仍以学生实际作答为依据。


## 练习导入、切题与重点确认

保留原始作答，并在分析前确定可靠的输入。

### 2.1 上传练习材料

用户进入 App 的“练习导入与确认”，选择清晰的试卷或作业图片。图片应保留题干、自己的演算及必要批改，便于同时查看题目要求和实际处理过程。选择图片后，页面显示上传与识别进度，处理完成后进入本次材料的确认界面。

### 2.2 OCR 切题与结构化记录

浏览器把图片提交给 Express 后端。后端保存材料记录，通过腾讯云 SDK 调用 QuestionSplitOCR，取得题目区域和识别文字，再整理为带有题号、题干、作答及区域坐标的题目记录。OCR 负责图像识别，后续智能体负责学习分析。

区域坐标将页面中的题目记录与原图位置联系起来。用户可以对照图像核查识别内容，尤其注意公式、负号、根号范围和手写步骤；题目编号则把材料、确认结果与后续发现连接起来。

上传图片 → OCR 切题识别 → 原图与文字核对 → 保存重点题

### 2.3 第一次重点人工确认

用户勾选需要分析的题目；没有识别到作答时，可按页面提示补录，并填写必要备注，然后点击“保存错题确认”。原始错误步骤应保留，订正答案与原作答分清，使分析能够定位问题发生的位置。

这次确认用于降低识别错误、材料遗漏和选题偏差对分析的影响。确认结果保存后，应用按本次选择组织题干、作答和备注，交给学习内容分析任务；未选择的题目保留在材料记录中。


## 智能体分析：从证据到发现

先解释本次作答，再提出值得保留的学习线索。

### 3.1 启动任务与组织上下文

用户进入“分析与记忆”，选择已完成重点题确认的材料，点击“开始分析”。后端读取题干、原始作答、备注和相关教材节点，并筛选有关的已接受记忆，组织成结构化输入。随后在服务器上启动 Hermes，加载指定 Skill，通过 DeepSeek 模型 API 完成理解、分析与生成。

### 3.2 学习内容分析 Skill 的处理顺序

1. **核对证据**：检查题目要求与作答是否对应，区分学生演算、批改信息和备注，明确哪些内容可以支持判断。

2. **定位具体问题**：对照实际步骤解释主要问题，同时保留已做对的部分；只有最终答案时，说明正确关系并保留错因未知。

3. **联系知识与历史**：用教材节点解释相关概念，参考必要的历史观察。比较以新的作答为准，明确判断适用于哪道题、哪个步骤。

4. **形成发现与建议**：生成有来源的局部发现，给出与原题直接相关的行动，再判断是否存在值得用户确认的记忆候选。

### 3.3 结构化输出与结果检查

这一处理方法在当前 App 中由“已确认错题分析”Skill 执行。输出以 JSON 组织，每条 finding 对应一道题，记录发现内容、作答依据、问题类型、确定程度、教材关联、行动建议及候选记忆。应用检查字段、题目关联和引用后，将结果保存并展示为分析卡片。

学习证据是材料事实，学习发现是对事实的解释，记忆候选则是可能值得以后参考的观察。将这三层分开，可以让用户检查结论从哪里来，再决定是否保留。


## 分析结果确认与学习记忆

由用户决定哪些观察进入后续学习上下文。

### 3.4 第二次重点人工确认

分析完成后，用户阅读发现内容、作答依据和建议，对照原题判断是否符合自己的实际情况。在待确认记忆区域，对认可的观察选择“接受”，对不适合保留的候选选择“忽略”。接受决定保存后，该观察才成为后续任务可调用的学习记忆。

学习证据 → 局部发现 → 记忆候选 → 人工确认 → 已接受记忆

第一次确认检查输入，第二次确认检查模型提出的观察。两次确认分别减少输入错误与分析偏差继续传播，保留学生对自己学习记录的判断权。用户接受某条记忆后，后续分析仍应结合新的作答重新核对。

### 3.5 记忆保存哪些信息

| 记录层次 | 保存内容 | 后续用途 |
| --- | --- | --- |
| 学习发现 | 本次问题、原始依据、知识关联与行动建议 | 解释本题，并进入本周综合 |
| 记忆决定 | 候选内容、接受状态、来源题目与分析记录 | 明确哪些观察经用户认可 |
| 已接受记忆 | 可供复用的观察及来源关系 | 作为后续分析与周报的比较线索 |

### 3.6 记忆怎样进入下一次任务

SQLite 保存业务记录。新任务到来时，应用按用户和学科读取已接受记忆，再依据知识点关联及文本匹配筛选有关内容，随当前材料交给 Hermes。模型由此获得有来源的历史上下文，持续性来自应用的数据保存与任务组织。

未被接受为记忆的学习发现，仍可参与本周报告；接受记忆也不等于已经执行建议。这样既保留本周材料的完整性，又避免把一次判断变成固定标签。


## 周报生成：调取本周材料与记忆

以自然周为周期，将分散记录整理为统一的分析上下文。

### 4.1 定期回顾与生成操作

用户可在每周学习整理时进入“周报与打印”，点击“生成周报”。应用汇总服务器当前自然周的学习记录，任务完成后保存报告；用户可查看、打印，并选择其他周期的历史报告。当前入口由用户触发，按周进行定期回顾。

### 4.2 周报调用哪些信息

| 上下文 | 选取方式与作用 |
| --- | --- |
| 本周学习发现 | 按同一用户、同一学科和自然周读取；同一题保留对应的最新分析，避免重复生成增加证据数量。 |
| 原题与实际作答 | 回查题干、学生演算和已有备注，让周报能够核对先前分析的依据。 |
| 行动与记忆决定 | 读取对应建议及候选的接受状态，理解已经提出什么、用户认可什么。 |
| 相关已接受记忆 | 按知识点与文本关联筛选，提供有来源的历史线索；同一来源的记忆与发现不重复计数。 |
| 教材知识节点 | 提供相关知识参照，帮助组织重点和说明复习方向。 |

### 4.3 建立可追溯的证据目录

后端生成报告范围 report_scope 与证据目录 evidence_catalog。范围说明周次及材料数量，目录将每条发现关联到题目、作答与来源。周报模型引用 evidence_ref，应用再将其转换为用户可阅读的证据详情。

这种组织方式让模型专注于综合判断，日期和数量由应用提供。单题分析、候选记忆与已接受记忆即使同时出现，也仍需回到原始题目核对其独立性。


## 周报生成：聚合见解与行动

让本周最重要的问题、变化和下一步清楚可见。

### 4.4 周报生成 Skill 如何综合

Hermes 加载周报生成 Skill（weekly_learning_report），调用 DeepSeek 处理应用准备的上下文。Skill 首先要求核对发现与原始作答，再比较不同题目的处理过程，判断哪些证据能够共同支持一个学习重点。

| 综合方向 | 判断依据 |
| --- | --- |
| 重复问题 | 不同题目出现相同的可见处理错误，能够说明具体环节反复出现问题。 |
| 局部变化 | 按时间比较对应步骤，说明后一次做对了什么，同时保留仍存在的问题。 |
| 明确的单次问题 | 证据清楚且影响后续学习，可单独列为需要关注的重点。 |
| 仍需观察 | 答案或表现存在问题，但现有过程不足以确定原因，保留待观察事项。 |

聚合见解来自证据之间的联系，而不只是标签出现的次数。历史记忆帮助寻找值得比较的线索，本次作答决定判断是否成立；材料只有一次时，报告就围绕这次材料组织重点。

### 4.5 从重点到可执行建议

周报按“本周总览—关键见解—仍需观察—下一步行动”呈现，优先突出一至两个重点。每项行动说明要做什么、怎样做及如何检查，并关联支撑该行动的题目证据。用户可以展开依据，回到具体步骤理解复习安排。

### 4.6 报告保存与后续衔接

应用校验模型返回的结构、引用和行动关联，补充权威周次与证据详情后保存报告。新作答进入系统后，再成为下一次比较的依据。周报负责综合和建议，记忆更新仍经过用户决定；分析方法则通过开发者维护的 Skill 版本持续改进。


## 系统架构与 AI 能力

组件部署、真实调用链与智能体工作流程。

系统分为三个位置：学生设备上的浏览器、项目自己的腾讯云 VPS，以及外部 OCR 和大模型服务。VPS 是租用的云服务器，部署了网页服务、应用后端、Hermes 和数据存储；DeepSeek 模型本身不部署在这台 VPS 上。

### 5.1 组件部署在哪里，怎样相互调用

浏览器、项目 VPS 与外部云服务共同完成一次学习任务。下一页按组件列出运行位置、调用接口与交换内容。


## 部署位置与组件调用

从浏览器请求到云端模型，再到结果保存。

| 能力或组件 | 部署／运行位置 | 谁调用它、通过什么接口 | 职责与交换的内容 |
| --- | --- | --- | --- |
| Web 工作台 | 学生设备的浏览器；页面由 VPS 提供 | 学生操作页面，页面向后端发送 HTTP API 请求 | 上传图片、确认错题、查看任务和分析结果；不直接调用云端模型 |
| Nginx 网关 | 项目 VPS | 接收浏览器请求，提供网页并转发 API 请求 | 提供统一访问入口，分别承接演示和真实应用 |
| Express 应用后端 | 项目 VPS | 接收网页请求，分别调用 OCR、Hermes 和存储 | 组织任务、准备输入、检查输出、保存结果并返回页面 |
| 腾讯云 `QuestionSplitOCR` | 外部腾讯云 OCR 服务 | 后端通过腾讯云 SDK 调用云 API | 接收练习图片，返回题目区域及识别文字；不是 Hermes 内部的识图步骤 |
| Hermes Agent | 项目 VPS 上的本地程序 | 后端通过本地进程启动命令行任务，传入结构化数据并接收结果 | 加载指定 skill，结合本次材料组织模型任务；无需学生打开 Hermes 界面 |
| 项目自定义 skills | 版本化文件随项目部署到 VPS | 后端选择任务对应的 skill，由 Hermes 加载 | 保存分析步骤、判断边界和输出要求；不是另一个云服务 |
| DeepSeek 大模型 | 外部模型服务 | Hermes 通过配置的模型 API 调用 | 根据 skill 和任务材料完成理解、推理与生成；应用后端不直接调用它 |
| SQLite 与私有文件 | 项目 VPS | 应用在本机读写；不开放给浏览器或模型直接操作 | 保存题目、分析结果、记忆决定与报告，供后续任务按需取用 |

一次真实任务中，浏览器先把练习交给后端，后端调用 OCR，再将识别结果交学生确认。确认后，后端选择相关题目、教材知识和已接受记忆，连同指定 skill 交给 Hermes。Hermes 调用 DeepSeek 生成分析，应用检查结果后保存并展示。这里的“本地 Hermes”是相对 VPS 而言，不是运行在学生电脑上；模型推理仍通过网络完成。


## Hermes 与可复用的 Skills

5.2 把验证过的经验固化为分析方法。

本项目使用 Hermes 的重点，不只是“替应用调用一次大模型”，而是把学习分析中逐步积累的经验整理为可复用、可检查、可修改的 skills。模型提供通用理解和推理能力，skill 则说明：在这个学习场景里，应当怎样使用这些能力。

一份 skill 可以理解为“分析方法手册”：需要哪些材料，先检查什么，怎样对照题目与学生作答，什么证据足以支持判断，什么时候应保留未知，以及怎样给出学生看得懂的结果。它主要以文字组织方法和要求，不是把每道题的答案写成固定程序，也不是重新训练模型权重。程序仍需检查格式与来源，开发者仍需检查数学和内容质量，不能只靠 skill 保证正确。

例如，实践发现模型可能根据一个错误答案补想学生未写出的步骤。值得沉淀的经验不是“记住这道题应该答什么”，而是更通用的方法：**先区分可见作答与推测；只有答案时，不把某条可能的错误过程当成事实。**再如，学生这次正确求出了 b，却在后面算错，分析就应保留做对的部分，而不是沿用旧记忆笼统地说“仍然不会求 b”。

这些经验写入 skill 后，后续任务可以沿用同一套分析方法，不必每次聊天重新解释。它们保存在项目文件中，开发者能够阅读、比较版本、修改和回退。更换模型时，这些方法仍可作为起点，但必须重新验证效果，不能假定表现不变。


## Skills 的迭代与核心职责

5.3 运行、检查、修订、再验证。

经验不是让模型写出一份长提示词就自动获得，而是在有反馈的迭代中形成：

代表性案例 → 运行当前 Skill → 核对实际结果 → 提炼通用经验 → 修订 Skill → 用旧案例和新变体复验

这个闭环中，先检查问题来自哪里：图片识别错了，就处理输入；题目与历史记录对应错了，就修正应用；分析方法有问题，才修改 skill。不能把所有问题都变成新增提示词。复验既看原来的问题是否改善，也看其他题目是否出现退步，保留失败记录，不把一次好答案当成稳定能力。

**可持续积累的成果，是分析方法、代表性案例和验证记录，而不只是某次生成的漂亮答案。**目前由开发者在 AI 辅助下完成这套迭代，再把选定的 skill 版本交给应用使用；不是每次学生使用后，智能体都会自动改写自己的技能。

这里还要区分两种积累：**skills 保存“怎样分析”的通用方法，学生记忆保存“这个学生此前出现过什么”的个体线索。**前者经过开发验证更新，后者经过学生接受后由应用保存。题目变多会增加可比较的证据，但不等于 skill 或模型已经自动学会了更好的方法。

上述是开发质量的反馈闭环。学生收到建议后，是否练习、是否有效、如何再调整，是另一条学习反馈闭环；当前提供建议和后续作答比较，尚未实现完整的行动执行与效果跟踪。

### 5.4 两个核心技能

**错题分析技能：看清这一次。** 读取已确认错题的题干、学生作答和相关知识，生成有依据的学习发现、建议以及可选的记忆候选。先看实际步骤，不因为学生选了错题就编造错误原因。

**周报生成技能：联系多次练习。** 综合本周学习发现及其原始作答，参考必要的已接受记忆，区分重复问题、局部变化和原因未知，给出优先行动。单次答对某一步，不等于整个知识点已经掌握。


## 开发过程与关键改进

6.1 从想法到流程，6.2 从流程到设计选择。

### 从想法到可用流程

发现学习中的问题 → 说清需求并拆成小任务 → 与 AI 讨论设计 → AI 辅助编码与验证 → 人工运行、核对结果 → 修改并继续验证

开发先从一条完整使用路径出发：学生上传练习、确认错题、阅读分析，再查看周报。围绕这条路径分别实现网页、数据保存和 AI 服务连接，用少量代表性题目检查每一步，最后再把它们串起来。

早期先用 Demo 和预置样例验证功能流程与交互，再逐步接入真实服务，避免在需求尚未清楚时就投入复杂部署和付费调用；接入后仍保留 Demo，方便稳定展示与比较。

### 设计中做出的三个选择

**先做什么：把精力放在学习分析上。** 图片识别交给成熟的 OCR 服务，教材知识先离线整理。学生确认错题后，系统再分析作答。这样既控制开发规模，也不要求 AI 一次包办教材处理、识别和判卷。

**记住什么：保存线索，不给学生贴标签。** 例如，一道题漏求一次函数中的 b，能说明这次步骤不完整，却不能直接说明学生一直不理解截距。系统把可能值得关注的内容列为记忆候选，由学生决定是否保留；以后再遇到相关题目，仍要以新的作答为准。

**怎样看变化：让周报回到题目本身。** 只统计“二次根式错误两次”，还不足以说明两次错在同一处。周报同时读取分析记录和原始作答，比较具体步骤，再决定是不是重复问题、哪一步有变化。学生不需要先接受每条分析为记忆，才能把它纳入本周报告。

## 真实运行、反思与 AI 协作

8.1 检查分析质量，8.2 使用 AI 辅助开发。

### 一次真实的实践与反思

单题实践曾比较同一道题的两种输入：一种保留错误步骤，另一种只给最终答案。有步骤时，可以指出错误发生在哪里；只有答案时，模型却可能补想学生没有写出的过程。实践也发现，增加分析规则虽然能改善某些表述，却可能引出新的数学或证据问题。

因此，项目没有把“规则越多、解释越长”当成进步。没有明显收益的候选修改没有采用，失败输出也保留。单题目标收敛为解释本题、指出可见问题、保留不确定性；更深入的共性判断交给后续多次练习比较。随后用多批材料检验重复问题、局部变化和原因未知，而不是只展示一道表现最好的题。

检查时不仅看程序有没有成功返回，还要核对数学是否正确、结论有没有作答依据、建议能不能执行。小样本能帮助发现问题，但不能用来宣称系统整体准确率。

### 怎样使用 AI 辅助开发

项目采用 AI 辅助开发：用编程助手帮助理解代码、实现功能、排查问题和整理验证；由人确定目标、检查结果并决定是否采用修改。系统中的学习分析 AI 与开发时使用的编程助手，是两种不同用途。

### 开发方式

项目采用 Vibe Coding：我表达需求、设计架构，借助 AI 编程助手实现和修改，再核对运行结果并决定采用哪些变更。
