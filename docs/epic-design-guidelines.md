# Epic 设计文档规范

本规范适用于 V2 及后续版本。它明确允许具有合适复杂度的 Epic 建立独立设计文档，使 developer、AI agent 和未来维护者共享同一份可版本管理的设计上下文。

Epic 设计文档不是重治理要求，也不是每个功能的必备材料。它的价值是把跨模块边界、关键约束、失败处理和实现证据放在一个稳定位置，减少重复推导和协作漂移。

## 什么时候适合建立

出现以下任一情况时，Epic owner 可以建立独立设计文档：

- 跨越多个模块、进程或用户流程状态，需要明确职责和数据流；
- 引入或改变数据库、持久化 schema、migration、任务队列、缓存或其他长期状态；
- 新增或改变 API、数据 contract、领域语义或外部 Provider 边界；
- 需要设计事务一致性、失败恢复、回滚、兼容或降级行为；
- 涉及隐私、安全、凭证、外部费用或不可逆数据影响；
- 多位 developer 或 AI agent 需要跨会话协作，单靠 Issue 描述不足以稳定传递上下文；
- 抽象架构已经明确，但需要一份具体计划把边界落实到文件、接口、数据流和验收证据。

Epic owner 无需为了创建或实施普通设计文档单独申请批准。涉及真实数据或隐私、外部费用、账号权限和不可逆迁移时，由实际执行的共同维护者记录影响、保护措施、验证和恢复方式。

## 什么时候不需要建立

以下工作通常直接使用 Issue、PR、代码和测试即可：

- 局部 bug 修复、文案或样式调整；
- 不改变外部行为的普通重构；
- 单一模块内、风险较低且容易从代码理解的功能；
- 临时调试步骤、任务清单或逐文件施工日志；
- 只为设想中的未来能力预先设计当前并不需要的框架。

不要把“一个 Child Issue 一份设计文档”作为默认流程。一个复杂 Epic 默认维护一份主设计文档；只有出现边界独立、需要长期单独维护的 contract 时才拆分。

## 位置和命名

版本内的 Epic 文档统一放在：

```text
docs/v<major>/epics/e<epic-number>-<short-slug>.md
```

例如：

```text
docs/v2/epics/e1-persistence-api.md
```

文件名表达 Epic 成果或子系统，不使用 `notes`、`review-final`、`new-design-v2` 等临时名称。文档必须从对应版本 README 和 GitHub Epic Issue 链接，保证 developer 和 agent 可以发现。

## 状态与能力声明

文档开头至少标明：

```text
Status: Proposed | Implementing | Implemented | Superseded
Epic: E<number> / GitHub Issue
Owner: developer name
Updated: YYYY-MM-DD
```

- `Proposed`：设计中或已经评审，但能力尚未实现。
- `Implementing`：正在实现，文档需要随重要偏差更新。
- `Implemented`：代码、迁移、验证证据和用户路径均已具备。
- `Superseded`：已被其他文档或架构替代，必须链接替代位置。

设计被接受不等于能力已经实现。文档中必须区分 `current`、`proposed`、`future` 和 `unknown`；没有运行证据时不能把计划描述成当前能力。

## 推荐内容

根据 Epic 实际风险选择必要章节，不要求机械填满模板：

1. **成果与用户场景**：这个 Epic 让用户或系统获得什么能力。
2. **范围与非目标**：当前负责什么，明确延后什么。
3. **已验证基线**：当前代码、数据和运行能力；未知项保持 `unknown`。
4. **核心不变量**：少量不可破坏的行为，通常不超过五条。
5. **边界和数据流**：模块所有权、接口方向和主要状态变化。
6. **失败与恢复**：预期失败、稳定状态、回滚、重试、兼容和隐私影响。
7. **当前阶段实施映射**：拟修改的模块、contract、migration 和关键顺序；未来阶段只写方向。
8. **验收与证据**：命令、测试、迁移验证和用户可见路径。
9. **接受的残余与延后能力**：不阻塞当前成果的限制和明确的后续触发条件。
10. **需要 ADR 的决定**：会跨 Epic 或跨版本约束未来实现的选择。

规范要求应能关联到真实用户场景、失败后果、责任边界和代表性验证。不要用大量假设、排列组合或未来扩展把当前 Epic 变成完整系统规格书。

## 条件性设计复核

复杂 Epic 在大量编码前应做一次与风险相称的设计自检；需要第二视角时可以请求独立复核。复核不是批准实现权限，而是确认核心不变量已经能落实到具体接口、状态和证据。结论写在 Epic Issue；接受的修改直接合入同一份 Epic 设计文档，不另建 `review-final` 文档。

当 Epic 声称兼容既有 API 或 data contract 时，设计文档必须给出一张最小映射表：

| 项目 | 必须说明 |
| --- | --- |
| 接口或输出 | 具体 endpoint、job result 或持久化输出 |
| 权威 contract | 文件、schema 或在本文中定义的新响应 envelope |
| 版本与兼容规则 | 当前版本、必需字段、允许扩展和破坏性变化处理 |
| 验证方式 | 自动校验、字段/类型断言、消费者测试或明确的人工证据 |

示例形状不能自动等同于机器校验。如果仓库里的 contract 只是 example-shaped JSON，评审必须明确当前采用什么可执行检查，并把升级为 JSON Schema 或其他严格 schema 作为当前工作或明确延后能力。

当 Epic 涉及持久化、恢复或异步状态时，评审还必须把关键不变量绑定到代表性场景：

- 持久化必须验证跨进程重启，而不只是同一进程重新查询；
- 事务一致性必须验证包含合法和非法项的失败写入不会留下部分结果；
- 异步任务必须验证至少一个最终状态以及结果或错误读取，而不只检查初始 `pending`；
- fallback、poller 或恢复机制必须验证进程重启后的行为；
- 每条阻塞性评审意见必须指出违反的核心不变量、失败后果和最低修复证据。

负责维护者确认实现边界足够清楚后，文档可以从 `Proposed` 进入 `Implementing`；是否请求独立复核由风险和实际需要决定。这不表示能力已完成。

## 实现一致性复核

Epic 收口前做一次轻量实现一致性自检；需要时由独立 reviewer 提供第二视角。按已记录的设计检查代码和证据，不重新发明架构：

1. 核对每个核心不变量是否有代表性验证；
2. 对照接口—contract 映射检查版本、必需字段和消费者语义；
3. 复跑持久化、失败原子性、恢复和异步最终状态场景；
4. 将总体结论写入 Epic Issue，将可执行修正分别写入对应 Child Issue；
5. 所有阻塞项清除后，补齐用户或开发者可见的能力说明、验证、排除项和残余风险，再把文档改为 `Implemented`。

同一批低风险 Child Issue 可以在 Epic checkpoint 一次评审。只有具体修正需要回到对应 Child Issue，不为普通 review finding 额外创建 Issue。

## 与其他载体的分工

| 载体 | 负责内容 |
| --- | --- |
| Roadmap / Milestone | 版本方向和可发布成果 |
| Epic Issue | 实时状态、负责人、阻塞和协作入口 |
| 版本架构 | 跨 Epic 必须保持的稳定边界 |
| Epic 设计文档 | 当前 Epic 如何落实边界、处理风险并完成验收 |
| ADR | 为什么选择一个会长期约束后续工作的方案 |
| Schema / contract / migration / tests | 可执行的实现事实和验证依据 |
| PR / commit | 实际改动和验证记录 |

Epic 文档不复制 Project 状态，不替代 Issue，也不把示例 JSON 提升为高于机器 contract 的权威。

## Developer 与 AI Agent 的使用方式

1. Epic owner 在设计开始时创建或接管主文档，并从 Epic Issue 链接。
2. AI agent 先核对仓库现状，把未验证内容标为 `unknown` 或 `proposed`，再提出设计。
3. 在大量编码前做一次与风险相称的设计检查；涉及 contract、持久化或异步状态时执行上面的条件性检查，普通迭代不需要反复等待批准。
4. 实现中发现必要偏差时更新同一份文档，不另建 `final-v2` 等副本。
5. Epic 完成时补充代表性验证证据，并将状态改为 `Implemented`。
6. 将跨 Epic 的长期决定提炼到 ADR 或版本架构；将未完成内容明确留给后续 Epic。
7. 文档不再有效时标记 `Superseded`，不要让旧方案继续冒充当前事实。

## 轻治理底线

- 文档帮助自主开发，不用于把 Epic owner 变成等待逐项批准的任务执行者。
- 评审只阻塞数据丢失、错误外部写入、隐私或安全暴露、凭证风险、不可逆迁移，以及明确违反核心不变量的问题。
- 偏好、命名、额外防御和假设中的未来扩展可以记录为接受的残余或后续工作。
- 一旦主路径、关键边界和代表性失败验证已经满足，应进入实现或交付，不继续为了“更完整”无限扩写设计。
